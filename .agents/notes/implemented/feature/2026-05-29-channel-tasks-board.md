# Agent Note: Channel tasks board

Status: implemented

## Problem

A human watching a group of agents cannot answer "what is each agent doing, and what is blocked?" without reading the whole transcript. The shared workflow-task substrate that hybrid routing uses (`group_workflow_task`, `group_workflow_task_participant`, `group_workflow_event`) holds the right raw material but is group-only, admin-gated, has no single-assignee invariant, no blocked reason, no message-derived creation, a routing-oriented status enum (`pending`, `needs_human`, `needs_approval`, `completed`, …) and a lightweight detail-panel list for a UI. The hard part is not drawing columns; it is making the board trustworthy: agents that create too many tiny cards, cards that go stale, concurrent human and agent edits, and status changes that nobody can find because they never appear in chat.

## Decision

The workflow tables are promoted in place into a channel-task domain and exposed through a new `channel task` model, API and agent protocol; the physical names stay `group_workflow_*`. [`migrations/0025_channel_kanban_board.sql`](../../../../migrations/0025_channel_kanban_board.sql) hard-resets the unreleased legacy rows and tightens the row: `assignee_principal_id` NOT NULL with `ON DELETE RESTRICT`, `status` CHECK `todo | in_progress | blocked | in_review | done` (default `todo`), `blocked_reason`, `source_kind` (`agent | message`, `message` requiring `source_message_id`), `context_label`, `idempotency_key`, `idempotency_payload_hash`, `version` (starts at 1), the `description` column dropped, `group_workflow_event.resulting_version`, the per-conversation key allocator `channel_task_sequence`, and `principal.channel_visibility` (`visible | internal`). Board ownership is read only from `assignee_principal_id`; the service keeps exactly one `role_key = 'owner'` participant row in step for router compatibility (`group_workflow_task_single_owner_participant_idx`).

The service is `DbService::{list_channel_tasks, list_channel_task_exports, get_channel_task_detail, create_channel_task, create_channel_task_from_message, patch_channel_task}` in `crates/choruz-application/src/db_service/group_workflow_tasks.rs`; its `choruz_channel_task_*_total` counters live on the shared registry ([shared metrics registry](../architecture/2026-09-03-shared-metrics-registry.md)). The gateway plugin `services/choruz-api-gateway/src/plugins/kanban.rs` registers `GET|POST /v1/conversations/{conversation_id}/tasks`, `POST …/tasks/from-message`, `GET /v1/tasks/{task_id}` and `PATCH /v1/tasks/{task_id}` (handlers in `handlers_channel_tasks.rs`) only while `plugin_enabled(KANBAN_PLUGIN_ID)` from `crates/choruz-common/src/plugins.rs` is true under `CHORUZ_PLUGINS`. Task events are server-authored side effects of validated mutations; no public append-event route exists.

Mutation ordering is last-write-wins by server commit: no caller sends an expected version, `PATCH` is field-scoped (`NullablePatch<T>` distinguishes omitted, `null` and set, which is how `blocked_reason` is cleared), every accepted mutation increments `version` and appends a `group_workflow_event` carrying previous and new values plus `resulting_version`. Every user-visible surface (list, detail, sync payload, conversation export) goes through the deny-by-default projection `ChannelTaskSnapshot` / `ChannelTaskEventProjection` in `crates/choruz-application/src/types.rs`; raw `metadata.workflow`, routing role maps and internal agent ids never leave the service. Realtime is the sync feed: `trg_channel_task_sync_change` (`migrations/V026__sync_change_log.sql`) emits `channel_task.created | updated | deleted` identifier envelopes (`conversation_id`, `task_id`) to every active member, and `chat-app.tsx` answers with `queueChannelTaskRefetch`, keeping the newer row via `isChannelTaskNewer` in `lib/channel-tasks/channel-task-reconciliation.ts`.

## Data

Request and response types in `crates/choruz-application/src/types.rs`, all request structs `deny_unknown_fields`:

## Authorization

Boards exist for group conversations and direct conversations that include an agent (`require_channel_task_conversation_eligible_tx`). `create_channel_task` is available only to visible group agents (`require_visible_group_agent_actor_tx`), sets `source_kind = "agent"`, defaults an omitted assignee to the acting agent, and rejects a human assignee from an agent. `create_channel_task_from_message` is human-only, requires an assignee, generates `TASK-{N}` through `allocate_unused_task_key_tx`, and sets `source_kind = "message"` with the source id retained. An agent may patch a task it owns, transfer it from itself to another visible agent, or act on any task in a group where `conversation_runtime_policies.default_coordinator_agent_id` names it (`is_configured_channel_task_coordinator_tx`); a human may change status and assignee on any visible task, and only a human can assign a human. A valid assignee is an active member of the conversation in the same workspace, not disabled, not deleted, and not an `internal` agent, checked on every path (service, `visibleChannelTaskAssignees`, the roster query). Title editing after creation, a `description` field (`deny_unknown_fields`), empty-form human creation and agent commands in direct conversations do not exist.

## Idempotency

`task_create` requires a non-blank `idempotency_key` and dedupes on `(conversation_id, created_by, idempotency_key)`: the same key with the same canonical payload hash returns the existing card with `created == false`, and the same key with a different payload is `AppError::Conflict` (`409`). Create-from-message dedupes on `(source_message_id, created_by)` (`group_workflow_task_message_dedupe_idx`) and that rule wins over the idempotency key: a repeat with a changed title or assignee returns the existing card unmutated.

## Agent protocol

Agents mutate the board through three silent outbox commands, `task_create`, `task_update` and `task_transfer`, that `process_outbox_commands_with_stats` in `services/choruz-pipeline/src/outbox_handler.rs` routes to `process_channel_task_command` before the generic chat path; nothing reaches the timeline. `task_create` becomes `POST …/tasks`; `task_update` and `task_transfer` resolve `task_key` or `task_id` through `resolve_channel_task_ref` and become `PATCH /v1/tasks/{task_id}`. Each command yields a result envelope `{"command_type","ok","task_key","task_id","idempotency_key","emitted_at"}` (plus `error_code` and `message` on failure) that `persist_outbox_command_result` writes to `<workspace>/.choruz-outbox/results/<message_id>.json`; `agent-templates/extensions/command-results.md` tells agents how to react to `invalid_assignee`, `task_not_found`, `idempotency_conflict`, `channel_tasks_disabled` and the rest. With the plugin off, every task command fails closed with `channel_tasks_disabled`.

Roster and ownership context ride on every `[choruz-incoming]` envelope: `roster:[{"id","name","type","host"?}]` from `MemberProvider::list_assignee_roster` and `your_tasks:[{"task_key","title","status"}]` from `list_open_tasks_for_agent` (Postgres implementation in `services/choruz-pipeline/src/pg_member_provider.rs`), rendered by `build_prompt`, `format_assignee_roster` and `format_your_tasks_suffix` in `crates/choruz-router/src/router.rs`, capped at `MAX_HINTS = 20` and omitted when the agent owns no open card. The delivery mechanism is recorded in [Per-turn roster injection](../architecture/2026-08-18-per-turn-roster-injection.md), the coordinator output contract in [Board tasks created receipt](2026-08-18-board-tasks-created-receipt.md), and the rollout to existing workspaces in [Versioned bootstrap refresh](2026-08-18-versioned-bootstrap-refresh.md).

## Web surface

`plugins/kanban/client.tsx` contributes a `Tasks` tab beside `Chat` (`kanbanConversationTab`, `shouldShowChannelTasksTab`) and the "Create task" message action; `components/channel-tasks/channel-task-board.tsx` renders the five fixed columns with a `<select>` status menu and an assignee picker limited to `visibleChannelTaskAssignees`, and `components/channel-tasks/channel-task-create-modal.tsx` is the only place a title is edited. Human actions apply optimistically and `restoreChannelTaskAfterFailedMutation` rolls a rejected card back.

## Alternatives considered

- **New `channel_task`, `channel_task_event` and `channel_task_participant` tables with a backfill from the workflow tables** (the RFC's Option B): rejected because it needs backfill or dual writes, raises the risk that routing state and board state diverge, and moves more code before an MVP can ship; clean names were not worth a second task store.
- **A UI-only kanban over the existing workflow list** (Option C): rejected because it cannot serve direct conversations, enforce one assignee, define human-versus-agent mutation ordering or produce the history reporting needs; it leaves every trust problem to prompts.
- **A right-side detail-panel list**: rejected in favour of a primary `Tasks` tab in the conversation area, because the board is the surface a supervising human lives on rather than a secondary property sheet.
- **Optimistic concurrency with an `expected_version` on every write**: rejected because it asks agents and browsers to reason about versions; the latest accepted server commit wins, `version` orders sync payloads and audit, and field-scoped `PATCH` keeps a later agent status update from overwriting a human reassignment.
- **A chat message per task mutation**: rejected because it recreates the transcript noise the board exists to remove; mutations are silent, history lives in `group_workflow_event`, and failures reach the acting agent through the results file rather than the timeline.
- **A public append-event API**: rejected because events are audit records; they are created only as side effects of validated creation, patch, accepted agent commands or accepted workflow metadata.
- **Sync payloads carrying the full task snapshot**: rejected in favour of identifier envelopes plus an authorized refetch, so a payload can never leak more than the projection and clients converge from one canonical read.
- **Letting agents assign tasks to humans, or letting direct-conversation agents run task commands**: rejected for the first release; a task becomes human-assigned only by human action, and direct-conversation boards are human-maintained from message actions.
- **Long-form descriptions, post-creation title edits, empty-form creation, filters, due dates and priorities**: rejected to keep the board a progress-visibility surface rather than a project-management product; context comes from title, source message, context label, blocked reason and history.

## Consequences

- One task store serves routing and the board, so `metadata.workflow` handoffs and `task_*` commands cannot disagree about ownership; the price is group-oriented physical names and a service layer that must keep board state separate from routing-only participant roles.
- A later valid agent update can still surprise a human who just edited the same field; history preserves what happened, which is the accepted cost of not requiring versions on writes.
- Clutter control is instruction guidance plus the required title, the required idempotency key and the `your_tasks:` hint; no per-turn creation budget exists in code.
- Disabling the `kanban` plugin removes the routes, fails commands closed and hides the tab, so rollback is a configuration change; task rows stay in the database.
- Observability is `creates_total`, `updates_total`, `mutation_errors_total` and `load_errors_total` on `/metrics`, `channel_task_mutation_failed` with redacted detail, `channel_task_rapid_successive_update` for two patches within `CHANNEL_TASK_RAPID_UPDATE_SECONDS` (2 s), and `channel_task_workflow_reference_unresolved` for metadata naming an unknown task.
- The invariants are pinned by `channel_kanban_migration_hard_resets_legacy_workflow_rows_and_adds_constraints`, `workflow_task_service_synchronizes_assignee_owner_and_versioned_events`, `channel_task_generic_create_is_group_agent_only_and_idempotent`, `channel_task_assignee_validation_rejects_missing_invalid_and_cross_workspace`, `channel_task_real_internal_agent_provisioning_rejects_assignment_and_redacts_surfaces`, `channel_task_fanout_payload_shape_redacts_internal_metadata_and_orders_versions`, `conversation_export_includes_channel_tasks_with_safe_projection`, `disabled_kanban_plugin_does_not_register_routes` and `metrics_endpoint_reports_channel_task_mutation_counters` in `services/choruz-api-gateway/src/tests/`; `task_create_command_posts_to_gateway_as_non_chat_result`, `task_update_command_patches_gateway_as_non_chat_result` and `task_commands_are_rejected_as_non_chat_failures_when_gate_is_off` in `outbox_handler.rs`; `build_prompt_appends_your_tasks_when_agent_owns_open_cards`, `build_prompt_omits_your_tasks_when_no_open_assignments`, `format_your_tasks_suffix_caps_at_twenty_entries` and `build_prompt_sanitizes_roster_display_names` in `router.rs`.
- The web contract is pinned by `lib/channel-tasks/channel-task-assignees.test.ts`, `lib/channel-tasks/channel-task-reconciliation.test.ts` and `apps/web/tests/e2e/channel-tasks.spec.ts` ("repeated create-from-message dedupes and does not mutate the existing task", "server rejection rolls the card back instead of corrupting local state", "runtime assignee roster refreshes across added, removed, disabled, hidden, and restored agents").
