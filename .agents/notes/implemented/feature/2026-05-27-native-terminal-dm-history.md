# Agent Note: Native terminal DM history recovery

Status: implemented

## Problem

A direct chat with a terminal-driver agent is a live PTY bridged over `/v1/ws/terminals/{binding_id}`, not a list of `conversation_events`; Choruz never persists terminal bytes. After laptop sleep, a browser reload, a WebSocket reconnect or a gateway restart the browser-side buffer is gone, and the sidebar says "No messages yet" for a DM whose PTY held a whole conversation. The native CLIs keep their own session history on disk, and Claude Code, Pi, Grok and OpenCode expose a session id that can be handed back to a resume flag, but interactive Codex exposes no session id at startup, stores every session in a global date-bucketed `~/.codex/sessions` tree, and writes its `session_meta` record only after the first real turn. Guessing "the newest Codex file for this cwd" can attach another agent's, or another company's, transcript to a DM.

## Decision

Terminal DM history is restored by resuming the exact native CLI session, never by parsing native files into chat. `ensure_pty_session` in `services/choruz-api-gateway/src/handlers_terminals.rs` spawns the driver with `terminal_cli_args`: Claude `--resume <id>`, Pi `--session <id>`, Grok `--resume <id>`, OpenCode `--session <id>`, Codex `resume <id>`; the CLI repaints its own history into the existing xterm surface. On WebSocket disconnect the `PtySession` is removed from the pool and its `ProcessContainer` kills the process tree; continuity lives in the native session store plus the id Choruz keeps on the binding. No terminal route writes `conversation_events`, and there is no terminal-history API.

For every driver except Codex the resume id is `agent_runtime_bindings.external_session_id`, backfilled when empty by `RuntimeStore::sync_session_id_from_disk` (`crates/choruz-agent-runtime/src/binding.rs`), which reads the CLI's workspace-scoped session registry and stamps `external_session_provenance = workspace_scan_verified`; the same sync runs before disconnect cleanup so the id is captured while the process context is intact. For Codex, `terminal_resume_session_id` deliberately returns nothing: the Codex path resumes only from the binding-owned terminal anchor described below, so a headless or scanned id is never interpreted as terminal history.

Sessions that predate Choruz enter through import, not projection. `POST /v1/workspace-sessions/scan` and `POST /v1/workspace-sessions/import` (`services/choruz-api-gateway/src/handlers_workspace_sessions.rs`) list a workspace's sessions with `SessionCatalogScanner::scan` (`crates/choruz-agent-runtime/src/session_catalog.rs`: `~/.claude/projects`, `CODEX_HOME`, `PI_CODING_AGENT_SESSION_DIR`, `GROK_HOME`, the OpenCode binary) and adopt each selected one as a new agent principal, a direct conversation and a terminal binding whose `external_session_id` is the native id, with `config_json.native_session_import`, `external_session_provenance = workspace_scan_verified`, `external_session_mode = terminal` and an explicit `binary_path`. An imported Codex session is revalidated against its selected id and workspace path, copied into the binding-owned managed `sessions/` directory, and registered as a `terminal_session` with `provenance = workspace_scan_imported`; the resume validator accepts that provenance only when `native_session_import` matches the anchor. Import fails rather than guessing when the selected Codex session has no unique matching native history file. `native_session_import` (`migrations/0032_native_session_import.sql`) keeps the mapping idempotent per (`workspace_path`, `driver_type`, `native_session_id`) under the advisory lock `native_session_import_lock_key`; `migrations/V032__imported_sessions_use_terminal_ui.sql` and `migrations/V033__imported_sessions_set_harness_binary.sql` keep imported bindings on terminal drivers with a harness-specific binary so an imported Codex, Pi, Grok or OpenCode session does not launch Claude.

## Codex binding-scoped session store

`prepare_codex_spawn_if_needed` gives every Codex terminal binding a managed home from `provision_managed_codex_home`: `<choruz_runtime_dir()>/codex-homes/<binding_id>/` with `0700` permissions, a local non-symlink `sessions/` directory, and `config.toml`, `auth.json`, `plugins`, `skills` and `cache` symlinked from the user's `CODEX_HOME` (or the harness account's home from `harness_account_env`). A home that resolves inside the agent workspace, or whose `sessions/` escapes the canonical home, is refused. The process runs with `CODEX_HOME` pointing there, so "newest session file" is meaningful only inside a directory that exactly one binding owns.

Capture is baseline-driven and fails closed, and it runs at four points in the binding's life:

1. Before spawn, `RuntimeStore::begin_codex_terminal_capture` persists `config_json.terminal_capture` (`CodexTerminalCaptureMetadata`: the owner tuple, `native_home_path`, `sessions_path`, `spawn_started_at`, `baseline_session_files`, `binding_generation`); this survives a gateway crash that happens after Codex writes `session_meta` but before an anchor exists.
2. While the process runs, the bridge calls `try_capture_codex_terminal_session` on each startup output frame; `unique_codex_session_candidate` considers only JSONL files created under the canonical `sessions/` after the baseline whose first `session_meta` has `cwd` equal to the binding's `workspace_path`. Zero candidates leave the anchor absent; more than one abort with a warning rather than pick.
3. Before disconnect cleanup, `capture_codex_terminal_before_cleanup` reconciles once more so the id is persisted before `ProcessContainer` kills the CLI.
4. On the next open, `prepare_codex_spawn_if_needed` runs `reconcile_codex_terminal_session_from_capture` when `terminal_capture` is still present, which is the only disk resync path for Codex and never looks at the global `~/.codex/sessions`.

`write_terminal_session_anchor` replaces `terminal_capture` with `config_json.terminal_session` (`TerminalSessionAnchor`: `session_id`, `source = native_cli`, `provenance = terminal_process_captured`, `binding_id`, `conversation_id`, `agent_principal_id`, `company_id`, `driver_type`, `workspace_id`, `workspace_path`, `native_home_path`, `native_session_path`, `binding_generation`) only while `config_json.terminal_generation` still equals the generation that started the capture. The importer writes the same shape with `provenance = workspace_scan_imported` after it copies and validates the explicitly selected native file.

Resume validates the whole owner tuple. `codex_resume_session_id_from_anchor` accepts an anchor only through `RuntimeBinding::valid_terminal_session_anchor_for_context` (binding, conversation, principal, driver, workspace id and path, company, current generation, current managed home), then re-reads the anchored file, requires it to sit under the managed `sessions/` after symlink resolution, and requires its `session_meta` id and `cwd` to match. `rebind_workspace` and `POST /v1/companies/{company_id}/reset-sessions` (`handlers_runtime::reset_company_sessions`) strip `terminal_session` and `terminal_capture` and advance `terminal_generation`, so a delayed capture from an old process can never reattach. Any failure launches a fresh session and claims no restored history; `ensure_terminal` reports `resumed_session` only when a resume id is passed to a newly spawned process.

## Startup output and sidebar

The PTY reader in `ensure_pty_session` keeps a `startup_replay` buffer of up to 64 KiB while the broadcast channel has no subscriber; `take_startup_replay` drains it exactly once into the first WebSocket, so a resume repaint emitted before the browser subscribes is neither lost nor duplicated on reconnect. `conversationPreviewText` in `apps/web/lib/messages/sidebar-conversations.ts` returns no subtitle for a terminal DM with no database messages (`isTerminalDirectMessage`, passed as `hideEmptyPreview` from `apps/web/components/chat/sidebar.tsx`); a real preview is kept whenever one exists, and group previews are unchanged.

## Alternatives considered

- **Parse native session files into a read-only transcript projection** behind `GET /v1/conversations/{conversation_id}/terminal-history` with opaque cursor pagination: kept by the RFC as a second milestone and not built, because native resume-rendering restores the visible history and the agent's memory in one buffer, while projection needs version-tolerant parsers, signed cursors and path redaction for every driver.
- **Render recovered history as chat bubbles**: rejected because the interaction model is still a PTY and bubbles would make a terminal DM look like a normal conversation.
- **Preload recovered text into the xterm buffer from Choruz**: rejected because reconnect clears and pagination are awkward and recovered text is indistinguishable from live output; the CLI's own repaint gives the same continuity.
- **Write preview-only rows into `conversation_events`** to reuse sidebar preview, search and unread code: rejected because a partial database history looks durable, risks duplicates against a later transcript model and blurs the source-of-truth boundary; the empty subtitle is hidden instead.
- **Key native history on the principal, the workspace path or the native session id alone**: rejected because principals are rebound, workspaces are shared between agents and Codex ids live in a global namespace; the anchor carries the full tuple plus a generation. A user-selected imported session is distinct: its exact native file is revalidated and copied into the binding-owned store before anchoring.
- **Match the newest global `~/.codex/sessions` file by cwd and time**: rejected as unsafe across agents created around the same time; a binding-local `CODEX_HOME` makes newest-after-baseline attributable.
- **Reuse `external_session_id` for Codex terminal resume**: rejected because the same binding can hold a headless or scanned id; terminal provenance is kept separate so a group session is never resumed into a DM.
- **Attach the WebSocket subscriber before spawning the child**: the other strategy the RFC allowed; the bounded replay buffer won because `ensure_terminal` and `terminal_input` spawn through the same pool without any socket attached.
- **An admin-only "repair history anchor" action**: rejected; when no safe source exists the DM shows a fresh terminal rather than asking an admin to guess.
- **Copy `auth.json` into each managed home**: rejected in favour of symlinks so credentials stay in one place under owner-only permissions.

## Consequences

- Codex history is guaranteed for terminal sessions launched through the managed home whose first real turn produced a binding-local file, and for imported sessions whose explicitly selected native file was revalidated and copied into that managed home; global sessions are never attached by guessing.
- How much history reappears is whatever the CLI repaints; there is no pagination or search over terminal DMs and no durable Choruz transcript.
- Every managed home carries symlinked credentials, so it lives outside the workspace with `0700` and local paths are redacted from errors (`redact_local_path_error`).
- Sidebar previews for terminal DMs stay empty until something is written to the database.
- The headless path keeps its own guard: `session_provenance_matches` in `services/choruz-pipeline/src/executor.rs` resumes `external_session_id` only when `external_session_mode` is `headless`.
