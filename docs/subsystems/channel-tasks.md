# Channel tasks

Channel tasks are the kanban board attached to a group (or agent direct) conversation: cards with a status column, one visible assignee, an append-only event history, and three silent agent commands that mutate the board without chat noise. A reader can use this page to trace a card from the `task_create` command or the "Create task" message action through the gateway routes and `DbService` into `group_workflow_task`, and to see how the `roster:` and `your_tasks:` envelope fields keep agents honest about assignees. Source: [`../../crates/choruz-application/src/db_service/group_workflow_tasks.rs`](../../crates/choruz-application/src/db_service/group_workflow_tasks.rs) with the gateway plugin in [`../../services/choruz-api-gateway/src/plugins/kanban.rs`](../../services/choruz-api-gateway/src/plugins/kanban.rs).

## Data

`group_workflow_task` (after 0025): `id`, `conversation_id`, `task_key`, `title`, `status` (CHECK `todo | in_progress | blocked | in_review | done`, default `todo`), `assignee_principal_id` (NOT NULL, FK `principal` ON DELETE RESTRICT), `blocked_reason`, `source_kind` (`agent | message`; `message` requires `source_message_id`), `context_label`, `idempotency_key`, `idempotency_payload_hash`, `version` (BIGINT, starts at 1), `created_by`, `created_at`, `updated_at`, with `UNIQUE (conversation_id, task_key)` from 0024. The `description` column does not exist. Unique indexes: `group_workflow_task_agent_idempotency_idx (conversation_id, created_by, idempotency_key)` and `group_workflow_task_message_dedupe_idx (source_message_id, created_by)`.

`group_workflow_task_participant` keeps exactly one `role_key = 'owner'` row per task (`group_workflow_task_single_owner_participant_idx`), synchronized from `assignee_principal_id` for routing compatibility. `group_workflow_event` rows carry `resulting_version`. `channel_task_sequence (conversation_id, next_value)` backs generated keys of the form `TASK-{N}` (`allocate_unused_task_key_tx`).

Rust request and response types in [`crates/choruz-application/src/types.rs`](../../crates/choruz-application/src/types.rs): `ChannelTaskStatus`, `ChannelTaskSourceKind`, `CreateChannelTaskRequest { task_key?, title, assignee_principal_id?, status?, context_label?, idempotency_key }`, `CreateChannelTaskFromMessageRequest { message_id, title, assignee_principal_id, context_label?, idempotency_key? }`, `PatchChannelTaskRequest { status?, assignee_principal_id?, blocked_reason: NullablePatch, context_label: NullablePatch }`, `ChannelTaskSnapshot` (adds `assignee_name`, `assignee_type`, `created_by_type`, `updated_by_type`, `version`), `ChannelTaskEventProjection` (`previous` / `new` as `ChannelTaskEventVisibleValues`, `workflow_kind`, `status_effect`, `reason_code`), `ChannelTaskDetailResponse`, `ChannelTaskExport`, `ChannelTaskCommandFailure`. The request structs are `deny_unknown_fields`, so `description` or `source_kind` in a body is a validation error.

`NullablePatch<T>` distinguishes an omitted field (`Unchanged`), JSON `null` (`Clear`) and a value (`Set`), which is how `PATCH` clears `blocked_reason`.

Envelope types in [`crates/choruz-router/src/models.rs`](../../crates/choruz-router/src/models.rs): `AssigneeRosterEntry { principal_id, display_name, principal_type, runtime_host_name? }` serialized as `{"id","name","type","host"?}` in `roster:[…]`, and `AssignedTaskHint { task_key, title, status }` serialized in `your_tasks:[…]`.

Web types in [`lib/api/choruz-types.ts`](../../apps/web/lib/api/choruz-types.ts): `ChannelTask` (`task_id`, `conversation_id`, `task_key`, `title`, `status`, `assignee_principal_id?`, `source_kind`, `version`, …), `ChannelTaskEvent`, `ChannelTaskDetail`, `ChannelTaskStatus`, `ChannelTaskSourceKind`, and `Principal.channel_visibility`.

Command result envelopes are JSON files under `<workspace>/.choruz-outbox/results/<message_id>.json`: `{"command_type","ok":true,"task_key","task_id","idempotency_key","emitted_at"}` on success, or `{"command_type","ok":false,"error_code","message","task_key","task_id","idempotency_key","emitted_at"}` on failure (`channel_task_command_failure`).

## Entry points

HTTP routes exist only while the `kanban` plugin is enabled; the manifest advertises host capabilities `channel-task-api` and `channel-task-events` and client capabilities `conversation-tab` and `message-action`.

| Route | Handler (`handlers_channel_tasks.rs`) | Service call |
|---|---|---|
| `GET /v1/conversations/{conversation_id}/tasks` | `list_channel_tasks` | `DbService::list_channel_tasks` |
| `POST /v1/conversations/{conversation_id}/tasks` | `create_channel_task` | `DbService::create_channel_task` (agent-only, idempotent) |
| `POST /v1/conversations/{conversation_id}/tasks/from-message` | `create_channel_task_from_message` | `DbService::create_channel_task_from_message` |
| `GET /v1/tasks/{task_id}` | `get_channel_task` | `DbService::get_channel_task_detail` |
| `PATCH /v1/tasks/{task_id}` | `patch_channel_task` | `DbService::patch_channel_task` |

- Web client calls: `fetchChannelTasks`, `fetchChannelTask`, `createChannelTaskFromMessage` and `patchChannelTask` in [`lib/api/choruz-api.ts`](../../apps/web/lib/api/choruz-api.ts) wrap these routes.
- Agent outbox: `"$CHORUZ_SEND" '{"type":"task_create","group":"proj-team","title":"…","assignee":"backend-engineer","idempotency_key":"…"}'`, `{"type":"task_update","group":"…","task_key":"TASK-3","status":"blocked","blocked_reason":"…"}`, `{"type":"task_transfer","group":"…","task_key":"TASK-3","assignee":"qa-engineer"}`. `process_outbox_commands_with_stats` routes these three types to `process_channel_task_command` before the generic single-command path, collects each envelope into `OutboxProcessResult.command_results`, persists it to the results directory and removes the maildir file; nothing is written to the chat timeline.
- Conversation resolution for commands: `conversation_id` if present, else `group` name via `resolve_group_conversation_id`; the agent token comes from `read_agent_token`; `task_create` becomes `POST …/tasks`, `task_update` / `task_transfer` resolve `task_id` or `task_key` through `resolve_channel_task_ref` and become `PATCH /v1/tasks/{task_id}`.
- Envelope: every routed `[choruz-incoming]` line carries `roster:[…]` recomputed by `list_assignee_roster` at delivery time, and `your_tasks:[…]` when `list_open_tasks_for_agent` returns open (non-`done`) cards for the receiving agent (capped at `MAX_HINTS = 20`, titles trimmed to 120 chars with `|` and control characters removed).
- Web: `kanbanConversationTab.isVisible` (`shouldShowChannelTasksTab`) shows the Tasks tab for group conversations and for direct conversations with a visible, enabled agent; `chat-app.tsx` calls `fetchChannelTasks` on tab open, `patchChannelTask` from the status menu and assignee picker, `createChannelTaskFromMessage` from the message action, and `queueChannelTaskRefetch` on `entity_type === "channel_task"` sync changes.
- Export: the conversation export in [`handlers_companies.rs`](../../services/choruz-api-gateway/src/handlers_companies.rs) includes `list_channel_task_exports`.
- Provisioning: team templates provisioned through `group_provisioning_job` ([`V017__onboarding_template_provisioning.sql`](../../migrations/V017__onboarding_template_provisioning.sql), statuses `validating` → `creating_agents` → `creating_group` → `adding_members` → `posting_kickoff` → `completed`) and `agent_provisioning_checkpoint` ([`V024__agent_provisioning_idempotency.sql`](../../migrations/V024__agent_provisioning_idempotency.sql)) populate the group whose members become the roster; `group_template_role_assignment.action = 'skipped'` roles never appear in it.

## Invariants

- Every card has exactly one visible assignee: `assignee_principal_id` is NOT NULL and the single-owner participant index keeps `group_workflow_task_participant` in step; pinned by `workflow_task_service_synchronizes_assignee_owner_and_versioned_events` and `channel_kanban_migration_hard_resets_legacy_workflow_rows_and_adds_constraints` in [`services/choruz-api-gateway/src/tests/workflow_tasks.rs`](../../services/choruz-api-gateway/src/tests/workflow_tasks.rs).
- An assignee is a conversation member in the same workspace, not disabled, not deleted, and not an `internal` agent, on every path (service validation, `visibleChannelTaskAssignees`, the roster query); pinned by `channel_task_assignee_validation_rejects_missing_invalid_and_cross_workspace`, `channel_task_real_internal_agent_provisioning_rejects_assignment_and_redacts_surfaces`, [`lib/channel-tasks/channel-task-assignees.test.ts`](../../apps/web/lib/channel-tasks/channel-task-assignees.test.ts) and the e2e "runtime assignee roster refreshes across added, removed, disabled, hidden, and restored agents".
- `task_create` is idempotent per `(conversation_id, created_by, idempotency_key)` and create-from-message per `(source_message_id, created_by)`; a repeat returns the existing card (`created == false`) without mutating it; pinned by `channel_task_generic_create_is_group_agent_only_and_idempotent` and the e2e "repeated create-from-message dedupes and does not mutate the existing task".
- `version` increases by one per successful patch and `group_workflow_event.resulting_version` records it; the web keeps the newer row via `isChannelTaskNewer`; pinned by `channel_task_fanout_payload_shape_redacts_internal_metadata_and_orders_versions` and [`lib/channel-tasks/channel-task-reconciliation.test.ts`](../../apps/web/lib/channel-tasks/channel-task-reconciliation.test.ts).
- Task commands never produce chat: they are dispatched before `process_single_outbox_command` and only emit result envelopes; pinned by `task_create_command_posts_to_gateway_as_non_chat_result` and `task_update_command_patches_gateway_as_non_chat_result` in `outbox_handler.rs`.
- `your_tasks:` is omitted when the agent owns no open card and lists at most 20; pinned by `build_prompt_appends_your_tasks_when_agent_owns_open_cards`, `build_prompt_omits_your_tasks_when_no_open_assignments` and `format_your_tasks_suffix_caps_at_twenty_entries` in `router.rs`.
- Roster names are sanitized (`sanitize_roster_display_name`) so a display name cannot break the envelope; pinned by `build_prompt_sanitizes_roster_display_names`.
- Coordinator role templates require the `Board tasks created` receipt and never a prose `Assignments` section; pinned by [`lib/groups/team-templates.test.ts`](../../apps/web/lib/groups/team-templates.test.ts) and [`lib/groups/team-template-renderer.test.ts`](../../apps/web/lib/groups/team-template-renderer.test.ts).
- With the plugin disabled no task route is registered and commands fail closed; pinned by `disabled_kanban_plugin_does_not_register_routes` and `task_commands_are_rejected_as_non_chat_failures_when_gate_is_off`.

## Failure modes

- Plugin disabled (`CHORUZ_PLUGINS` without `kanban`): HTTP routes are absent; each task command returns `error_code: "channel_tasks_disabled"` in its result file and the web hides the Tasks tab because the host manifest list from the bootstrap omits `kanban`, so `resolveClientPluginIds` drops the client plugin.
- Bad command payloads surface as `ok:false` envelopes with `missing_target`, `missing_assignee`, `invalid_assignee`, `missing_task`, `missing_title`, `validation_failed`, `idempotency_conflict`, `task_not_found`, `group_not_found`, `forbidden`, `unauthorized`, `gateway_error`, `gateway_unavailable`, `event_store_unavailable`, `agent_token_unavailable` or `unsupported_command`; `command-results.md` tells agents how to react to each.
- Service failures log `event = "channel_task_mutation_failed"` with `error_kind` and `error_detail_redacted = true`, and bump `choruz_channel_task_mutation_errors_total`; load failures bump `choruz_channel_task_load_errors_total`. The counters (`choruz_channel_task_creates_total`, `choruz_channel_task_updates_total`, `choruz_channel_task_mutation_errors_total`, `choruz_channel_task_load_errors_total`) are `common::metrics` counters registered in `group_workflow_tasks.rs`, forced to `0` by `DbService::new`, and served by every `/metrics` endpoint (`metrics_endpoint_reports_channel_task_mutation_counters`).
- Two patches within `CHANNEL_TASK_RAPID_UPDATE_SECONDS` (2 s) log `event = "channel_task_rapid_successive_update"` with the changed field list; workflow metadata that names an unknown task logs `channel_task_workflow_reference_unresolved`.
- A rejected web mutation rolls the card back with `restoreChannelTaskAfterFailedMutation`; pinned by the e2e "server rejection rolls the card back instead of corrupting local state".
- Roster lookup failure in the router logs `list_assignee_roster failed; envelope will use an empty roster` and delivers `roster:[]`; a `list_open_tasks_for_agent` failure omits `your_tasks:`.
