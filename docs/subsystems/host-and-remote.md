# Host and remote

The host-and-remote subsystem is everything that runs a Choruz backend somewhere other than the developer's shell and reaches it from somewhere else: the embedded-PostgreSQL-plus-supervisor crate, the headless `choruz-server` binary that SSH clients start, the `choruz` CLI that launches it locally, the `choruz-connector` that executes Agent turns on another machine, the Cloudflare Worker that relays end-to-end-encrypted Remote Control traffic, the web Server Manager that opens SSH tunnels, and the `infra/host` and `infra/ops` scripts that run and package the stack. A reader can use this page to find which binary emits the `CHORUZ_LISTENING=<port>` handshake, which routes a connector calls, which env vars each script reads, and which tests pin the readiness and fencing rules. Source: [`crates/choruz-supervisor`](../../crates/choruz-supervisor/src/lib.rs), [`services/choruz-server`](../../services/choruz-server/src/main.rs), [`apps/choruz-cli`](../../apps/choruz-cli/src/main.rs), [`services/choruz-connector`](../../services/choruz-connector/src/main.rs), [`services/remote-control-gateway`](../../services/remote-control-gateway/src/index.ts), [`infra/host`](../../infra/host/common.sh), [`infra/ops`](../../infra/ops/bin/release.sh).

## Data

`common::HostServiceStatus { status, service, protocol_version, database }` with `HOST_SERVICE_PROTOCOL_VERSION = 1` ([`crates/choruz-common/src/lib.rs`](../../crates/choruz-common/src/lib.rs)) is the versioned identity every `/readyz` returns; the supervisor, `infra/host/common.sh` (`service_ready`) and the CLI `status` command all read it.

`EmbeddedPg { database_url }` boots PostgreSQL on port 5433 as user `postgres`, database `choruz`, with `pgdata`, `pg-install` and `pgpass` under `dirs::data_dir()/choruz`; applied files are tracked in `_migrations (filename, applied_at)` and, for `CONCURRENTLY` migrations, per statement in `_migration_statement_progress (filename, statement_index)`.

`Supervisor::start_backend` spawns `choruz-api-gateway` on 3000 with `CHORUZ_DATABASE_URL`, `CHORUZ_ATTACHMENT_DIR=.choruz-runtime/attachments`, `CHORUZ_API_HOST=127.0.0.1`, `CHORUZ_API_PORT=3000`, `RUST_LOG`, then `choruz-pipeline` on 3020 with `CHORUZ_PIPELINE_METRICS_HOST` and `CHORUZ_PIPELINE_METRICS_PORT=3020`. The children run from the source workspace in development or from the binary directory in a complete bundle containing `choruz-api-gateway`, `choruz-pipeline`, and `migrations/`.

The stdout handshake is one line, `CHORUZ_LISTENING=<port>`, printed by `choruz-server` after both children pass readiness; every other log line goes to stderr. Readers are `start_host` in the CLI and `connect_choruz_tunnel` in the gateway.

SSH types in [`apps/web/lib/api/choruz-api.ts`](../../apps/web/lib/api/choruz-api.ts): `SshHost { name, hostname, user, port, identity_file }` and `SshTunnel { id, host, local_port, remote_port, pid, started_at, generation, status: "ready" | "disconnected", disconnected_at?, last_error? }`; the gateway request `ConnectChoruzRequest { host, remote_binary }` lives in `handlers_ssh.rs`.

Remote Control rows: `remote_control_pairing (id, principal_id, credential_hash, expires_at, consumed_at, created_at)` and `remote_control_device (id, principal_id, name, session_key_wrapped, paired_at, last_seen_at, revoked_at)`; web types `RemoteControlSettings { gateway_url, gateway_ticket }`, `RemoteControlPairing` (adds `credential`, `expires_at`) and `RemoteControlDevice { id, name, paired_at, last_seen_at }` in [`apps/web/lib/remote/remote-control.ts`](../../apps/web/lib/remote/remote-control.ts).

Runtime host rows: `runtime_host (id, company_id, name, token_hash, status ∈ online|offline|revoked, last_seen_at, created_at, updated_at, revoked_at)` and `runtime_host_pairing (id, company_id, code_hash, created_by, expires_at, consumed_at, created_at)`; a binding is placed on a host through `config_json->>'runtime_host_id'` and a queued command through `metadata->>'runtime_host_id'` (the V029 partial indexes). A connected device holds one host link (`GET /v1/ws/runtime-hosts/link`, [`services/choruz-api-gateway/src/host_link.rs`](../../services/choruz-api-gateway/src/host_link.rs)): the gateway's `RuntimeHost::Linked` sends every `HostRequest` and terminal operation over it and the device streams terminal output back, so a binding on a remote device gets the same terminal DM, directory listing, session scan and Codex home as one on the gateway's device. A device without a link is `not connected` (409) to every request. `native_session_import.runtime_host_id` makes the same native session identity independent on different devices. Web types `RuntimeHost { id, company_id, name, status, last_seen_at, created_at }` and `RuntimeHostPairing { code, expires_at }`.

Connector wire types in [`services/choruz-connector/src/main.rs`](../../services/choruz-connector/src/main.rs): `ConnectorConfig { api_url, relay, host_id, host_name, host_token, max_concurrency }` (JSON file, mode `0600`), where exactly one of `api_url` or the encrypted `RemoteCredentials` transport is used; `PairResponse { host: HostView { id, name }, host_token }`; `ClaimedCommand { command_id, attempt_id, binding_id, agent_id, conversation_id, turn_id, prompt, driver_type, workspace_path, model, external_session_id, harness_account, metadata }` (`binding_id` names the mirror the turn's outbox is shipped into, `metadata.attachments` the files to stage); and `CompleteCommand { attempt_id, succeeded, contents, error, tool_calls_count, execution_duration_ms, external_session_id, clear_external_session }`.

Worker bindings in [`wrangler.toml`](../../services/remote-control-gateway/wrangler.toml): Durable Objects `GatewayRoom` (`ROOMS`), `PairingRateLimiter` (`RATE_LIMITERS`), `CapabilityStore` (`CAPABILITIES`), secret `GATEWAY_AUTH_SECRET`, and `MAX_FRAME_BYTES = 1_000_000`.

## Entry points

The Worker also hosts Online account authentication at `/v1/online/auth` through
`src/online-auth.ts`. Better Auth owns password hashing, sessions and rate limits;
`ONLINE_DATABASE` is its D1 store and `ONLINE_AUTH_SECRET` is its signing secret.
This service receives account credentials over HTTPS; it is not the encrypted
chat relay. A signed-in Online account grants no Remote Control capability.
Before enabling the service, apply its separate D1 migrations with
`pnpm --dir services/remote-control-gateway exec wrangler d1 migrations apply choruz-online-accounts --remote`
and set `ONLINE_AUTH_SECRET` using `wrangler secret put`. The service fails closed
when either binding is missing. Local tests apply the same migration to isolated
D1 state. Email is a login identifier, not verified ownership; email verification
and password recovery are not exposed by this account surface.

Online transport uses `/v1/online/connect` with a bearer session and the
`OnlineMailbox` Durable Object (`ONLINE_MAILBOXES`). `/v1/online/links` creates
a bilateral delivery grant; `/v1/online/links/{id}/join` consumes its invitation,
and deleting the link revokes delivery. Neither endpoint grants runtime access.
`crates/choruz-relay-client/src/online.rs` owns the headless client, heartbeat,
reconnection and routing-bound ciphertext validation. A session expiring or
being replaced stops reconnection. Each account has one active socket, 256
pending ciphertexts and seven-day retention; an application acknowledges a
delivery after durable processing. The client emits acceptance separately from
writing to its socket, so callers retain their outbox until acceptance.
`online-transport.test.ts` exercises the real Worker/D1/WebSocket boundary;
the Rust socket test exercises disconnect/reconnect without a browser.

`choruz-server` (no arguments): resolves the migrations directory as `<exe dir>/migrations` if it exists, else `<workspace root>/migrations`; runs `EmbeddedPg::setup_and_start`, `Supervisor::start_backend`, `start_child_monitor`; prints `CHORUZ_LISTENING=3000`; blocks until SIGINT/SIGTERM (`ctrlc`) or `backend_failed()`; then `Supervisor::shutdown` and `EmbeddedPg::stop`. A distributable headless bundle keeps `choruz`, `choruz-server`, `choruz-api-gateway`, `choruz-pipeline`, and `migrations/` together under `bin/`; two binaries alone are insufficient because `choruz-server` owns the two backend children.

`choruz start` (`Command::Start` → `start_host`): reuses a ready loopback host or picks the binary from `CHORUZ_SERVER_BINARY` or the `choruz-server` sibling of the running `choruz` executable. A new host starts in a detached OS session with stdin closed, stderr appended to the platform data directory's `choruz/choruz-server.log`, and its PID written to `choruz/choruz-server.pid`. The CLI reads the one-time `CHORUZ_LISTENING=` stdout handshake, logs in on `http://127.0.0.1:<port>` (password `CHORUZ_OPERATOR_PASSWORD`, default `choruz-local`, or `CHORUZ_SESSION_TOKEN`), calls `GET /v1/remote-control/settings` and `POST /v1/remote-control/pairings`, prints the pasteable credential and exits without owning the server process. Other CLI variants are `Command::Status` (probes `/readyz` on `CHORUZ_API_BASE_URL` and `CHORUZ_PIPELINE_URL`), `CompanyList`, `AgentList`, `RemoteStatus` and `RemotePairingCredential`. The CLI installs the `ring` rustls provider before constructing an HTTPS client, so a workspace release containing another provider remains deterministic.

Remote SSH routes (plugin id `remote-ssh`, gated by `CHORUZ_PLUGINS`): `GET /v1/ssh/hosts` (parses `~/.ssh/config` and `ssh -G`), `POST /v1/ssh/tunnel`, `GET /v1/ssh/tunnels`, `DELETE /v1/ssh/tunnel/{id}`, `POST /v1/ssh/connect-choruz`. `connect_choruz_tunnel` runs `ssh <host> 'stdbuf -oL <remote_binary> 2>&1 || <remote_binary>'`, reads `CHORUZ_LISTENING=`, calls `pick_free_port()`, then holds `ssh -L <local>:localhost:<remote> -N <host>`.

`ServerManager` in the web app calls `listSshHosts`, `listSshTunnels`, `connectChoruzSshTunnel` and `deleteSshTunnel`, opens `http://localhost:<local_port>` on success, and shows `REMOTE_SERVER_INSTALL_COMMAND` (`cargo build --release -p choruz-server && cp target/release/choruz-server ~/bin/`) as the remote prerequisite.

Remote Control routes (plugin id `remote-control`): `GET /v1/remote-control/settings`, `POST /v1/remote-control/pairings`, `POST /v1/remote-control/pairings/redeem`, `GET /v1/remote-control/bridge-config`, `GET /v1/remote-control/devices`, `DELETE /v1/remote-control/devices/{device_id}`, `PUT /v1/remote-control/devices/{device_id}/seen`, `POST /v1/runtime-host-onboarding`, the runtime-host operation routes, plus `/v1/workspace-sessions/scan` and `/v1/workspace-sessions/import`. `POST /v1/remote-control/pairings` obtains a host capability, opens the host socket, and only then returns the credential; `remote_control_pairing_host` keeps the one-time ECDH handshake in the API runtime until it completes or expires. `remote_control_bridge::spawn` (started from [`lib.rs`](../../services/choruz-api-gateway/src/lib.rs)) runs one `maintain_bridge` task per principal that has an unrevoked `remote_control_device`, connects to the Worker with `connect_async`, offers the transport room to paired devices and marks `device.hello`; `remote_control_executor::RelayExecutor` executes the paired dashboard's `http.*` frames against `CHORUZ_INTERNAL_API_URL` / `CHORUZ_INTERNAL_WEB_URL` (defaults `http://127.0.0.1:${CHORUZ_API_PORT|3000}` and `http://127.0.0.1:${CHORUZ_WEB_PORT|3100}`) (allow-list: `/api/v1/*` → API with a bearer token, other `/api/*` → Next.js with the session cookie, `/api/v1/remote-control/*` refused) and multiplexes `/v1/ws/sync` and `/v1/ws/terminals/*` as `stream.*` frames, chunked at `CHUNK_BYTES = 384 KiB`; see [docs/operations/remote-control.md](../operations/remote-control.md#dashboard-relay). Host-side env: `CHORUZ_REMOTE_CONTROL_GATEWAY_URL` (unset means `HOSTED_GATEWAY_URL`), `CHORUZ_REMOTE_CONTROL_GATEWAY_SECRET`, `CHORUZ_REMOTE_CONTROL_PAIRING_SECRET`.

Runtime host routes, human side: `POST /v1/companies/{company_id}/runtime-host-pairings`, `GET /v1/companies/{company_id}/runtime-hosts`, `PUT` and `DELETE /v1/runtime-hosts/{host_id}`, `POST /v1/runtime-hosts/{host_id}/operations` (`filesystem.home`, `filesystem.list`, `workspace_sessions.scan`, `workspace.provision`, answered over the host link), `/v1/runtime/bindings/{binding_id}/host` (`assign_binding_host`), and the account sign-in routes `POST /v1/companies/{company_id}/harness-accounts/{account_id}/logins`, `GET .../logins/{login_id}`, `POST .../logins/{login_id}/callback` ([`handlers_harness_logins.rs`](../../services/choruz-api-gateway/src/handlers_harness_logins.rs)). Connector side, authenticated by the `x-choruz-host-token` header (`require_host`): `POST /v1/runtime-host-pairings/redeem`, `POST /v1/runtime-hosts/{host_id}/heartbeat`, `/commands/claim?wait_ms=<ms>` (long-poll capped at 25 000 ms), `/commands/{command_id}/heartbeat`, `/commands/{command_id}/complete`, `GET /commands/{command_id}/attachments/{attachment_id}` (`download_command_attachment`, only a file the claimed command names, under the agent's attachment access), `/bindings/{binding_id}/outbox` (`ship_binding_outbox`, at most 200 commands, only for a binding placed on that host), `/harness-accounts`, `/harness-accounts/{account_id}/verify`, and `/harness-account-logins/claim`, `{login_id}/publish`, `{login_id}/callback/claim`, `{login_id}/complete`, `{login_id}/fail`.

`choruz-connector pair --api-url <url> --code <8 digits> --name <machine> [--config <path>] [--max-concurrency <n>]` retains direct API pairing for private-network deployments. `pair-relay` receives the Remote Control credential and runtime-host code through stdin, completes a reverse encrypted pairing, redeems the code through an ephemeral loopback proxy, and writes the resulting config. `run` rebuilds that proxy when `relay` credentials are present, heartbeats, claims commands under a `Semaphore(max_concurrency)`, executes account-login jobs, and keeps the host link open (`maintain_host_link`: a direct WebSocket to `api_url`, or a relay stream opened with `RelayHttpClient::open_stream`), over which `choruz_host_runtime::link::run_device_link` answers every `HostRequest` and runs the device's terminals; `CHORUZ_RUNTIME_DIR` defaults to `~/.choruz/runtime` for the managed Codex homes. A remote turn refreshes the workspace's instruction file with `ensure_claude_md` and stages the message's attachments into `.choruz-inbox/` (`stage_command_attachments`) before it spawns, as the pipeline does locally. The outbox commands an agent writes on the device (`share_file`, `provision_agent`, `create_group`, `set_cron`, the `task_*` board commands, and a terminal DM's `send`) are shipped to the binding's controller-side mirror in shipments of at most 200 commands and 16 MiB of serialized commands: `ship_outbox` after each headless turn and `ship_pending_outboxes` every 2s for live terminals; a terminal's command files stay in its workspace until the controller has stored them, a headless turn's commands that could not be delivered wait in `<CHORUZ_RUNTIME_DIR>/outbox-spool/<binding_id>` for the same loop, and a shipment the controller refuses (`ShipError::Refused`: a client error other than 401, 408 or 429, as when the binding moved to another device) is dropped with a warning instead of retried ([`crates/choruz-host-runtime/src/outbox.rs`](../../crates/choruz-host-runtime/src/outbox.rs)). Agent provisioning on a remote host sends the rendered instruction file and selected skills as `workspace.provision`; the device creates the directory (under its own `~/.choruz/workspaces` unless a path was given) and installs the outbox helper. The API Gateway's `ConnectorSupervisor` discovers every JSON config under `~/.choruz/connectors/` and keeps one connector running for each. It checks the connector's file lock before spawning, restarts unexpected exits with delays from 500 milliseconds to 30 seconds, resets the failure count after a 60-second run, and stops a connector when its config is removed. `CHORUZ_CONNECTOR_BINARY` selects the executable. `RuntimeHostManager` ("Machines", "Add machine") calls `listRuntimeHosts`, `createRuntimeHostPairing`, `renameRuntimeHost`, `revokeRuntimeHost`.

A harness account signs in through the Harness's own browser flow wherever it lives. `crates/choruz-harness-login` drives Claude Code's stream-json control requests (`claude_authenticate` → `claude_oauth_callback`) or the Codex app-server browser login and reports the authorization link, callback state and verified account snapshot through a `LoginSink`. Claude Code returns an `authorization-code#state` value for manual login; Choruz separates the two fields and refuses a state from another login. Codex uses the `chatgpt` browser flow on both local and remote devices. A local browser reaches the app-server's loopback callback directly. For a remote device, the user opens the same link on the controlling computer and pastes the complete localhost callback URL; the connector requires matching state, accepts only an HTTP loopback redirect originally issued by its app-server, and forwards only code and state to that listener. Choruz waits for the matching completion notification before reading the account, exact quota and models. Claude account verification tolerates the short interval in which authentication is complete but the model catalog is not ready. Codex quota labels preserve the server's named rate-limit bucket and suppress only exact duplicate windows. For an account with a `runtime_host_id` the connector claims the `queued` row and reports through the host-facing routes above; for an account on the gateway's own device (`runtime_host_id` NULL) the gateway claims the row in the start transaction and runs the same driver in a spawned task that writes straight to `harness_account_login`. The binary comes from `CHORUZ_CLAUDE_BINARY` / `CHORUZ_CODEX_BINARY`, else `claude` / `codex` on `PATH`; Codex account login requires a CLI with `app-server` support. An `isolated` account gets its profile directory under `CHORUZ_HARNESS_ACCOUNT_ROOT` before the Harness starts. Credentials never pass through the sink or the database: the Harness writes them into that profile. Removing an account first disables every runtime binding that references it, then hides the account, so an Agent cannot continue with credentials that are no longer managed. A login the gateway was running when it restarted stays open until `expires_at` and then reads as `expired`; starting again queues a fresh one.

Worker HTTP surface: `GET /healthz`, `POST /v1/capabilities`, `GET /` and `/remote` (pairing dashboard), and `GET /connect` WebSocket upgrade with `?role=pair_client&pairing_id=<128-bit base64url id>` (rate-limited per `cf-connecting-ip`, resolved via `CapabilityStore` `/pair?pairing_id=`) or `?ticket=` (opaque capability or `verifyGatewayTicket` against `GATEWAY_AUTH_SECRET`). The credential's secret component never reaches the Worker. Deploy with `pnpm --dir services/remote-control-gateway run deploy`; set the secret with `pnpm exec wrangler secret put GATEWAY_AUTH_SECRET`.

Local host stack: `pnpm host:start`, `host:stop`, `host:status`, `host:smoke` wrap `infra/host/*.sh`; `infra/host/migrate.sh [up|down|reset|dropdb] [database_name]` tracks `_migrations`; `infra/host/web_e2e.sh [spec…]` runs `start.sh`, `migrate.sh reset`, `migrate.sh up`, builds `choruz-api-gateway` and `choruz-pipeline`, starts them plus `pnpm --dir apps/web dev`, waits on `/healthz` and the pipeline's `/readyz`, and runs `pnpm --dir apps/web e2e` (default `tests/e2e/app-smoke.spec.ts` unless `CHORUZ_WEB_E2E_FULL=1`). `infra/host/dev.sh` calls `pnpm host:start` and sources `infra/host/common.sh`.

`common.sh` reads `infra/host/.env`, falling back to `env.example`: `CHORUZ_PG_HOST`, `CHORUZ_PG_PORT`, `CHORUZ_PG_USER` (default `id -un`), `CHORUZ_PG_DB`, `CHORUZ_PG_PASSWORD`, `CHORUZ_PG_BIN`, `CHORUZ_INITDB_BIN`, `CHORUZ_PG_CTL_BIN`, `CHORUZ_CREATEDB_BIN`, `CHORUZ_DROPDB_BIN`, `CHORUZ_PSQL_BIN`, `CHORUZ_PG_DUMP_BIN`, `CHORUZ_API_HOST`, `CHORUZ_API_PORT`, `CHORUZ_WEB_PORT`, `CHORUZ_PIPELINE_METRICS_PORT`, `CHORUZ_RUNTIME_DIR`, `CHORUZ_DATA_DIR`, `CHORUZ_LOG_DIR`, `CHORUZ_ATTACHMENT_DIR`, `CHORUZ_BACKUP_DIR`, `CHORUZ_OPERATOR_WORKSPACE`, `CHORUZ_OPERATOR_USER`, `CHORUZ_OPERATOR_PASSWORD`, `CHORUZ_SESSION_SECRET`, `CHORUZ_SESSION_TTL_HOURS`. Exported `CHORUZ_PG_PORT`, `CHORUZ_API_PORT`, `CHORUZ_WEB_PORT`, `CHORUZ_PIPELINE_METRICS_PORT` override the file. In a git worktree `maybe_generate_worktree_env` writes a `.env` with `CHORUZ_WORKTREE_ROOT` and ports derived from `cksum` of the root: `54000+`, `30000+`, `40000+`, `50000+` offset.

Release and backup: `pnpm release:package` (`infra/ops/bin/release.sh package`) builds `choruz-api-gateway`, `choruz-pipeline`, `choruz-connector` and the Next.js standalone bundle into `releases/<timestamp>` and repoints `releases/current` and `releases/previous`; `release:deploy`, `release:rollback` (`rollback.sh`), `backup:create` (`backup.sh` → `database.sql`, `attachments/`, `agent_tokens.json`, `metadata.json`), `backup:restore` (`restore.sh`, validates `metadata.json`), `ops:check` (`check.sh`). Units: `choruz-api-gateway.service`, `choruz-pipeline.service`, `choruz-web-app.service`, `choruz-backup.service` + `choruz-backup.timer` (`OnCalendar=daily`), launchd `com.choruz.api-gateway`, `com.choruz.pipeline`, `com.choruz.web-app`; the Caddyfile proxies `/v1/*`, `/v1/ws/*` and `/healthz` to 3000 and everything else to 3100.

Closing Harness Accounts or changing its device does not cancel a sign-in. Reopen the account and choose Sign in to recover the existing link, callback input and current status. The start endpoint returns an unexpired open task with HTTP 200 and a newly created task with HTTP 201; only creation starts a driver. Explicit Cancel ends the task. Unsubmitted callback text is not retained across navigation.

## Invariants

- A listener on 3000 or 3020 is reused only when `/readyz` returns `HostServiceStatus` with the expected `service`, `protocol_version == HOST_SERVICE_PROTOCOL_VERSION` and `status == "ready"`; pinned by `readiness_probe_requires_service_identity_and_protocol` in `supervisor.rs` and by `service_ready` in `common.sh` (`protocol_version == 1`).
- `choruz-server` stdout carries only the handshake line: `tracing_subscriber` writes to stderr and `dup_stderr_to_stdio` routes children's stdout to the host's stderr.
- A child that exits after readiness sets `backend_failed`, triggers `shutdown()` and makes `choruz-server` exit 1; pinned by `child_check_reports_exit_after_readiness`.
- `stop_child` sends SIGTERM, waits `SHUTDOWN_GRACE` (3 s), then SIGKILLs and reaps; pinned by `stop_child_reaps_a_running_process`. `Drop for Supervisor` calls `shutdown()`.
- `remote_binary` is `choruz-server` or an absolute executable path (`is_safe_remote_binary`); pinned by `remote_binary_rejects_shell_metacharacters`. Tunnel generations fence stale connects; pinned by `newer_generation_fences_older_connection_attempts` and `managed_replacement_preserves_manual_tunnels`.
- Plugin routes exist only when `CHORUZ_PLUGINS` (unset means all built-ins) includes the plugin id; pinned by `disabled_remote_ssh_plugin_does_not_register_routes` and `legacy_ssh_connect_route_is_not_registered` in `tests.rs`.
- Runtime host pairing codes are eight digits, hashed with `keyed_hash(secret, "runtime-host-pairing", …)`, expire after `PAIRING_TTL_MINUTES = 10`, and are single-use; host tokens are stored only as `keyed_hash(secret, "runtime-host-token", …)`; pinned by `runtime_host_pairing_is_single_use_and_host_token_is_revocable`. `list_hosts` reports `offline` when `last_seen_at` is older than 45 seconds.
- Remote Control pairings use `v1.<128-bit id>.<128-bit secret>`, expire after `PAIRING_TTL_MINUTES = 5`, mix the secret into ECDH/HKDF, exchange role-bound transcript proofs and wrap session keys with AES-GCM at rest. The API establishes the host Gateway socket before returning a credential, and the socket remains owned by the API task after the HTTP request ends; this is pinned by `remote_control_pairing_redeem_and_revoke_round_trip` together with `pairing_credentials_contain_two_independent_128_bit_values`, `hashes_are_purpose_bound`, `session_keys_are_wrapped_and_authenticated_at_rest` and `transport_rooms_are_not_derived_from_long_lived_identity`. The bridge's envelope crypto is pinned by `encryption_round_trips_with_browser_wire_shape` and `malformed_encryption_iv_is_rejected_without_panicking`.
- The connector config file is written `0600` (`config_round_trip_is_private`); group replies count only when routed through the `CHORUZ_SEND` outbox (`routed_messages_preserve_each_helper_call`, `group_prompt_detection_parses_protocol_metadata_only`); `load_config` rejects `max_concurrency` of 0 or above 64; heartbeats use POST (`heartbeat_uses_the_runtime_host_post_contract`).
- The API Gateway owns connector children for its full lifetime. A newly written config is discovered without a restart, an unexpected exit is reaped and restarted with capped backoff, and removing the config terminates the child; pinned by `discovers_new_configs_restarts_crashes_and_stops_removed_connectors` in `crates/choruz-supervisor/src/connectors.rs`.
- A host ships outbox commands only for a binding whose `config_json.runtime_host_id` is that host (403 otherwise), a shipped `share_file` target must still resolve inside the workspace once symlinks are followed, and a shipped file over 8 MiB is refused before it is decoded. The mirror is laid out like a workspace outbox under `remote-outbox/<binding_id>/<host_id>` and keyed by the shipping host while the watcher drains every mirror of the binding, so a shipment accepted while the binding moved is still processed and a device is never told its commands were stored when nothing reads them. Each command keeps a SHA-256 receipt under `.choruz-outbox/receipts`: the watcher waits while the receipt is `pending`, an atomic move to `accepted` commits the shipment, an identical retry is a no-op even after the command was drained, and the same name with different content is rejected. Pinned by `stored_commands_land_in_the_mirror_like_a_workspace_outbox`, `an_accepted_shipment_is_not_republished_after_its_command_was_drained`, `a_shipment_name_cannot_be_reused_for_different_content`, `a_remote_command_waits_until_its_shipment_is_accepted`, the outbox section of `runtime_host_pairing_is_single_use_and_host_token_is_revocable`, and the existing confinement, size, mirror-drain, and connector retry tests.
- A remote filesystem operation is accepted only for an unrevoked host in a Company the human can access; the connector restricts paths to `HOME` or `CHORUZ_FS_BROWSE_ROOTS`, returns at most 500 entries, and caps operation responses at 8 MiB. Remote session import re-scans on that host immediately before mutation, records `native_session_import.runtime_host_id`, and binds the imported Agent to the same host.
- The Worker rejects frames over `MAX_FRAME_BYTES`, forwards only encrypted application frames in transport rooms (`isEncryptedTransportFrame`), and verifies ticket signatures and expiry (`verifyGatewayTicket`); pinned by `control.test.ts`, `tickets.test.ts`, `capability.test.ts`.
- `infra/host` scripts stop only processes whose `lsof` metadata, cwd and recorded start time match (`process_record_matches`, `stop_owned_process` returns 2 on mismatch); pinned by `infra/host/tests/process_lifecycle.test.sh`.

## Failure modes

- No `migrations` directory beside the binary or in the workspace: `choruz-server` logs `no migrations dir found` and exits 1. Embedded PostgreSQL failure logs `embedded postgres failed to start` and exits 1.
- Embedded PostgreSQL commands allow 60 seconds by default so first-run `initdb` works on slow disks; `CHORUZ_POSTGRES_COMMAND_TIMEOUT_SECS` accepts a positive integer override.
- Port 3000 or 3020 held by something that is not a ready Choruz service: `start_backend` fails with `port <port> is occupied by an incompatible or unready service`, `shutdown()` runs, exit 1. A child that never passes `/readyz` within `READY_TIMEOUT` (20 s) fails with `<name> did not become ready within 20s`.
- `choruz start` without a bundled binary: `could not find bundled choruz-server next to …; install a full Choruz release or set CHORUZ_SERVER_BINARY`; if the child exits before the handshake: `choruz-server exited before it became ready`. A Gateway connection failure prevents issuance of a credential but leaves the background host available for another `choruz start` attempt; inspect `choruz/choruz-server.log` in the platform data directory for host startup failures.
- `POST /v1/ssh/connect-choruz` without a handshake line reports `remote choruz-server never emitted CHORUZ_LISTENING line (is '<remote_binary>' installed on <host>?)` or a timeout; a tunnel whose `ssh` process dies shows `status: "disconnected"` with `last_error` (`exited_child_is_reported_as_disconnected`), which the Server Manager renders per host.
- Connector: a rejected direct pairing prints `pairing rejected with HTTP <status>`; a relay onboarding failure reports the last connector diagnostic without returning either credential; a connector that exits is restarted after a delay capped at 30 seconds, while a missing binary or persistently invalid config continues retrying at that cap; heartbeat failures log `host heartbeat failed`; a stale `attempt_id` on heartbeat or complete maps `SessionError::StaleAttempt` to `AppError::Conflict` (409); `revoke_host` bumps binding `epoch`, resets leased commands and revokes the token, so a disconnected connector cannot commit afterwards.
- Remote Control bridge: a dropped Worker socket logs `remote-control bridge disconnected` and reconnects with `reconnect_delay` backoff; a silent transport past `TRANSPORT_LIVENESS_TIMEOUT` (75 s) is dropped. The Worker answers 401 `Invalid or expired gateway ticket` and 404 `Pairing credential is invalid, expired, or not ready`.
- `infra/host`: a stale worktree `.env` is moved to `.env.backup.<timestamp>` and regenerated; a PID file whose PostgreSQL does not answer `SELECT 1` on the configured port is stopped and restarted; `restore.sh` refuses a backup whose `metadata.json` does not name `product: choruz` and the configured `CHORUZ_PG_DB`.
