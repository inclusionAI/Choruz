# Sync feed

The sync feed is how a browser stays current: a bounded `GET /v1/bootstrap` seeds the dashboard, then an authenticated `GET /v1/ws/sync` socket replays and streams the principal's durable `sync_change` rows, and each device acknowledges the cursor it has applied. Source: [`crates/choruz-application/src/db_service/sync.rs`](../../crates/choruz-application/src/db_service/sync.rs) and [`services/choruz-api-gateway/src/handlers_sync_ws.rs`](../../services/choruz-api-gateway/src/handlers_sync_ws.rs).

## Data

- `sync_change (cursor BIGSERIAL PK, principal_id, event_type, entity_type, entity_id, conversation_id, payload JSONB, created_at)` with index `idx_sync_change_principal_cursor (principal_id, cursor)`; one row per recipient principal, never deleted by a reader.
- `sync_device (principal_id, device_id, ack_cursor)` with PK `(principal_id, device_id)`, `ack_cursor >= 0`, and `device_id` between 1 and 128 characters without control characters.
- `application::SyncChange { cursor, event_type, entity_type, entity_id, conversation_id, payload, created_at }` and `SyncChangePage { changes, next_cursor, head_cursor, has_more }`; the client mirror is `DashboardSyncChange` in [`apps/web/lib/api/choruz-types.ts`](../../apps/web/lib/api/choruz-types.ts).

Change catalogue (trigger → recipients → `event_type` / `entity_type`):

| Source table | Trigger | Recipients | Events |
|---|---|---|---|

- WebSocket frames (`ServerFrame` / `ClientFrame` in `handlers_sync_ws.rs`): server sends `sync_ready { device_id, cursor, head_cursor }`, `sync_changes { changes, next_cursor, head_cursor, has_more }` (pages of `PAGE_SIZE = 200`), `sync_acked { cursor }`, `sync_error { detail }`, and a ping every 30 seconds; the client sends `sync_ack { cursor }`.
- `BootstrapResponse { principal, principals, companies, agents, conversations: { items, next_cursor, has_more }, plugins, hidden_conversations, runtime_bindings, sync_cursor, snapshot_at }`; each item is `BootstrapConversationResponse { conversation, last_message, last_activity_at, unread_count, mention_count, thread_unread_count, pinned_at, archived_at, hidden_at }`. `limit` defaults to 50 and is capped at 100; `after` is base64url JSON `{ last_activity_at, conversation_id }`.
- `DashboardSyncState { principal_id, device_id, ack_cursor }` is the per-browser record in IndexedDB; `device_id` comes from `crypto.randomUUID()`.
- Optimistic messages in the client cache carry `server_seq = OPTIMISTIC_SERVER_SEQ` (`Number.MAX_SAFE_INTEGER`) and the client-chosen `idempotency_key`.

## Entry points

1. `apps/web/app/dashboard/page.tsx` calls `fetchDashboardBootstrap(sessionToken, { limit: 100 })` and passes `bootstrap.sync_cursor` to `ChatApp` as `initialSyncCursor`, plus `conversations.next_cursor` / `has_more` for later pages.
2. `meta_handlers::bootstrap` reads `current_sync_cursor` first, then `list_conversation_bootstrap_page` (ordered by `COALESCE(conversation_activity.last_activity_at, conversation.updated_at) DESC, id DESC`, fetching `limit + 1` rows to compute `has_more`), and joins `list_principals_by_ids`, `list_accessible_agents`, `list_companies`, `get_unread_counts_for_conversations`, and `list_visible_hidden_conversations` with `tokio::try_join!`.
3. `applyBootstrap` in `chat-app.tsx` replaces or merges conversations, agents, plugins, companies, runtime bindings, flags (`useConversationFlags.applyBootstrap`), unread rows, and seeds `messagesByConv` with each `last_message` through `mergePreviewIntoMessages`, which never truncates cached history. Mode `append` (`/v1/bootstrap?limit=100&after=...`) loads older conversations; mode `refresh` (`/v1/bootstrap?limit=100`) reconciles the first page after a structural change.
4. `useChatWebSocket(userId, bootstrapCursor, onChanges, onParseError)` loads `DashboardSyncState` with `loadDashboardSyncState` (a stored cursor ahead of the bootstrap cursor is discarded and a new device registered), opens `ws(s)://<host>:${NEXT_PUBLIC_CHORUZ_API_PORT ?? 3000}/v1/ws/sync?device_id&cursor`, and reconnects with exponential backoff from 500 ms to 16 s.
5. `sync_socket` authenticates with `authenticated_principal`, waits for `SyncWakeupHub::wait_ready`, calls `register_sync_device` (`ack_cursor = GREATEST(stored, presented)`, rejected if the presented cursor is beyond the feed head), sends `sync_ready`, and drains pages with `list_sync_changes` until `has_more` is false.
6. Wakeups: `SyncWakeupHub` holds one `LISTEN choruz_sync_change` connection and broadcasts each notification payload (a `principal_id`, or `*` after a listener restart); `serve_socket` drains again when `is_relevant_wakeup` matches or the broadcast receiver lags.
7. The client applies each `sync_changes` page inside a serialised `applyChain`, persists `next_cursor` with `persistDashboardSyncCursor`, then sends `sync_ack`; `acknowledge_sync_device` stores `GREATEST(ack_cursor, cursor)` only when the cursor is at most the feed head, and the handler additionally refuses a cursor it has not sent on this connection.
8. `handleSyncChanges` routes by `event_type`: `message.created` builds a `ChatMessage` (`idempotency_key` from `payload.client_msg_id`) and calls `handleRealtimeMessage`, then `persistMessages`; `conversation.deleted` drops the conversation and its cache; pin, archive, and hidden events go to `useConversationFlags.applyChange`; `conversation.read_state_changed` and `thread.read_state_changed` trigger `refreshUnreadsDebounced` (`GET /v1/unreads`); `entity_type = 'channel_task'` queues a board refetch; everything else triggers the bootstrap `refresh`. A `runtime_binding.created` or `runtime_binding.updated` row re-reads that one binding through `GET /v1/runtime/bindings/{binding_id}` and upserts it into `runtimeBindings`; `runtime_binding.deleted` removes it; only an `event_type` no branch names falls back to a full `/v1/bootstrap` refresh.
9. `handleRealtimeMessage` merges with `upsertConfirmedMessage`, bumps the local unread badge for other conversations when `wsUnreadEffect(msg).bumpConversationUnread` is true, and refreshes thread counters when `refreshThreadUnread` is true; server counters stay canonical.
10. Reading: `POST /v1/conversations/{conversation_id}/view` runs `mark_conversation_viewed`, which fires `trg_conversation_read_sync_change` so every other device of the same principal refetches `/v1/unreads`; `POST .../threads/{thread_root_id}/view` does the same through `thread_read_receipt`.
11. Gap fill without a socket: `GET /v1/sync?cursor=<n>&limit=<1..500>` returns the same `SyncChangePage` read-only (default limit 100).
12. Optimistic reconciliation: `chat-app.tsx` inserts the pending bubble with `server_seq = OPTIMISTIC_SERVER_SEQ` and the client `idempotency_key`; the `POST /v1/messages` response and the `message.created` sync row both carry that key as `idempotency_key` / `client_msg_id`, and `upsertConfirmedMessage` replaces the optimistic entry in place, or removes it when the confirmed `id` is already cached, returning the same array reference when nothing changes.

## Invariants

- The feed is private per principal and never acknowledged globally; `list_sync_changes` filters on `principal_id`, and a device's `ack_cursor` only moves forward and never past `head_cursor`. Pinned by `sync_feed_is_gapless_private_and_independent_from_outbox_ack` and `sync_websocket_requires_auth_replays_unacked_and_isolates_device_acks` in [`services/choruz-api-gateway/src/tests/sync.rs`](../../services/choruz-api-gateway/src/tests/sync.rs).
- Notifications are wakeups only; the `sync_change` table is the source of truth, so a missed or coalesced `pg_notify` cannot lose data, and every listener (re)start broadcasts `*` to force a re-drain.
- `bootstrap` captures `sync_cursor` before reading the snapshot, so a change racing the snapshot may be replayed twice but can never be missed; pages are bounded and keyset-stable. Pinned by `bootstrap_is_bounded_stably_paginated_and_uses_activity_preview` and `bootstrap_caps_page_size_and_does_not_expose_foreign_conversations`.
- `list_sync_changes` fetches `limit + 1` rows and reports `has_more`, and it only returns rows with `cursor <= head_cursor` captured at the start of the call, so a burst larger than one page cannot skip its middle when the client persists `next_cursor`.
- A page is applied before its cursor is persisted and acknowledged, and pages are applied in order (`applyChain`), so a crash mid-apply replays the page. Pinned by `converges on one message in two tabs`, `deduplicates optimistic messages with sync confirmations`, and `reconnects without starting console or transcript polling` in [`apps/web/tests/e2e/websocket.spec.ts`](../../apps/web/tests/e2e/websocket.spec.ts).
- Agent replies reach the feed even though they bypass `outbox_event`: `trg_agent_reply_sync_change` projects every `event_type = 'reply'` row (written by `crates/choruz-writer/src/writer.rs`) to active members in the writer's transaction.
- Quiet thread replies never bump the conversation badge and the thread counter is never incremented locally, only refetched (`wsUnreadEffect` in `thread-unreads.ts`, `quiet_thread_reply_preserves_sender_unread_state`, and the `wsUnreadEffect` cases in [`apps/web/lib/messages/thread-unreads.test.ts`](../../apps/web/lib/messages/thread-unreads.test.ts)).
- `upsertConfirmedMessage` and `mergePreviewIntoMessages` never duplicate a bubble or truncate a conversation's cached history (`upsertConfirmedMessage` and `mergePreviewIntoMessages` suites in [`apps/web/lib/messages/messages.test.ts`](../../apps/web/lib/messages/messages.test.ts)).
- `device_id` is validated twice: `register_sync_device` rejects empty, over-long, or control-character ids, and the `sync_device` CHECK constraints enforce the same rule.

## Failure modes

- `LISTEN` connection lost: `SyncWakeupHub` flips `ready` to false, reconnects with backoff from 100 ms to 5 s, logs `dashboard sync LISTEN connection closed`, and broadcasts `*` once reconnected; new sockets fail with `500 dashboard sync unavailable` after a 5 s wait, and open sockets keep serving acks but receive no wakeups until the reconnect.
- Presented cursor ahead of the feed (for example a browser that outlived a restored database): `register_sync_device` and `list_sync_changes` return `400 sync cursor is ahead of this principal's feed`; the client pre-empts this in `loadDashboardSyncState` by resetting to the bootstrap cursor with a fresh `device_id`.
- Malformed client frame: server replies `sync_error { detail: "invalid sync frame" }` and keeps the connection; an ack beyond `last_sent` replies `cannot acknowledge an unsent cursor` and closes; a failed `acknowledge_sync_device` replies `sync acknowledgement failed` and closes.
- Apply failure in the browser (missing `sender_id`, `content`, or `server_seq` in a `message.created` payload, or an IndexedDB error): the hook emits the `dashboard_sync_frame_error` trace event, calls `onParseError` (which queues a channel-task refetch), closes the socket, and reconnects from the last persisted cursor so the page is replayed.
- Broadcast receiver lag (channel capacity 1024): the socket performs a full drain instead of dropping the notification.
- IndexedDB unavailable: `loadDashboardSyncState` falls back to an in-memory state with a new `device_id`, so each page load replays from the bootstrap cursor.
- Membership or workspace changes (`conversation.members_changed`, `principal.*`, `company.*`, `runtime_binding.*`) carry identifiers only; the client answers with a bootstrap `refresh`, so a burst of such rows costs one bounded `GET /v1/bootstrap` per page.
- Unread counters are written after the message commit and only warned on failure (see [store.md](store.md)), so the `unread_count` in a bootstrap item can trail a `message.created` row until the next `conversation.read_state_changed` or refresh.
